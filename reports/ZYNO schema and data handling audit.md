# Data handling, not schema alone, breaks ZYNO updates

ZYNO's failed updates and reads come mainly from **data handling in the generic API layer**, then from **schema patchwork**, and least from architecture in the abstract. The Supabase-style shim in `src/lib/db.ts` serialises a lossy, flat filter object into one Prisma proxy (`server/routes/db.ts`). That proxy runs unguarded `updateMany`/`deleteMany`, returns `{count}` instead of rows, and reports zero-row matches as success. The shim converts every failure into a resolved `{error}`, so callers that do not check it lose the failure. Behind that, the schema has ID-type mismatches (BigInt columns facing UUID entities), columns added only by hand-run SQL, and free-text statuses, which explain the failures that are loud and repeatable. Architecture contributes by letting three write paths with three validation levels reach the same table. Separately, a large share of business data (leases, cheques, vouchers, AP invoices, payroll, work orders) lives as untyped JSON blobs in `app_kv_store`, and many totals are computed in the browser. Every finding is static analysis of this repo only. Nothing was run and no database was contacted, so items marked inferred need a runtime check. Line numbers are exact where cited; some notes cited function names only.

## The generic proxy is the largest source of failed updates and empty reads

A UI call such as `db.from('leases').select(...).eq('id',x)` builds a query object in `src/lib/db.ts:5-205`. It reaches the server through `api-client.ts:20-38` and is executed by `server/routes/db.ts:179-252`. Updates go to `server/routes/db.ts:443-479`, which calls `updateMany` with a client-built `where`. Domain services (lease creation, PDC insert) are used only for inserts (`db.ts:16-22, 395-400`), not updates, so a lease update skips lease rules except termination. The failure modes are ranked below.

| Rank | Failure | Evidence |
|---|---|---|
| 1 | Empty or widened `where` updates or deletes every row. The only guards are for `properties`, posted vouchers and an `__no_match__` hack. | `server/routes/db.ts:456, 469-472, 495, 509-511`; `src/lib/db.ts:202-204` |
| 2 | Filters overwrite each other. `.gte().lte()` on one column keeps only the last operator. `.not()` ignores its operator, `.contains/.overlaps/.is` become equality, and unknown operators fall back to equality. | `src/lib/db.ts:35-60, 80-90, 106-109, 146-163` |
| 3 | PostgREST aliases such as `customers:customer_id(...)` are silently dropped, so joined objects come back undefined. Column lists are ignored and `*` is returned. About 62 alias-style selects exist. This is inferred and needs runtime confirmation. | `server/lib/coerce.ts` (`buildIncludeFromSelect`); `useLeases.ts:29-33, 49-53`; `leases-module.tsx:524`; `app-data-context.tsx:349` |
| 4 | Update returns `{count}`, but callers that chain `.select().single()` expect the row. | `server/routes/db.ts:469-474`; `src/lib/db.ts:200-204` |
| 5 | A zero-row update is reported as success, which hides stale ids and wrong id types. | `server/routes/db.ts:469, 509` |
| 6 | The shim never throws, about 96 empty catches exist, and an unknown table returns `{data:[]}`. | `src/lib/db.ts:230-249`; `server/routes/db.ts:232-239`; `assets-module.tsx:1598-2038` |
| 7 | `fetchAllRows` stops at the first error and returns partial data. It pages 1000 rows with no `ORDER BY`. | `app-data-context.tsx:302-321` |

Rank 7 means a mid-load error shows as missing units, leases or cheques beyond 1000 rows. The list is also inconsistent in a way that explains "get works, update fails" reports. Numeric-string ids are coerced in `where` (`server/lib/coerce.ts:65-67`) but not in write data (`coerce.ts:23-40`), so `eq('id','7')` works while writing `"7"` to an Int or BigInt column returns a generic 400. `sendDbError` hides which column failed (`errors.ts`), so the UI cannot show a useful reason. Two smaller findings are `upsert` as non-atomic find-then-write (`db.ts:332-351`) and array inserts that are sequential and non-transactional (`db.ts:424-431`). The tenant-role ticket flow likely returns 403 because `TENANT` is not in `OPERATIONS_RULE` (`db-policy.ts`; inferred).

## Schema defects produce the loud, repeatable write failures

The schema cause is concentrated and documented by the repo's own patch files. `fin_pdc_register` uses `BigInt` for `id`, `tenant_id`, `property_id`, `unit_id` and `bank_id` (`prisma/schema.prisma:847-860`), while customers, units and properties use UUID `VarChar(36)` (`schema.prisma:253, 3000`). The service layer then drops the mismatch silently. `numericOrNull` in `server/services/leases.ts:47, 70-76` keeps only all-digit values, so UUID tenant, property and unit references are stored as NULL with no error. `GET /api/finance/pdcs` filters this BigInt column by a UUID `tenantId` (`server/routes/finance.ts:16`) and would be rejected by Prisma. `fin_legal_receivables` has the same BigInt defect (`schema.prisma:796-809`). `fin_deposits` was fixed after the fact, and its migration comment says no deposit could be saved because `tenant_id` was a required bigint (`manual-migrations/2026-11-26-deposit-ids-text.sql:3-5`).

The second pattern is drift between `schema.prisma` and hand-run SQL. Columns were added only in SQL, so every write sending them failed: `fin_bank_accounts.status` ("every create/update that sent a status failed") and `fin_banks.status` ("Add Bank failed silently"), plus `leases.collection_status` and `units.market_rent`. Tables exist only in SQL (`fin_ar_invoices`, `fin_ap_invoices`, `fin_legal_cases`, `fin_payroll_runs`, `fin_bank_recon_records`, `app_kv_store`, `app_sequences`), so Prisma has no delegate and `coerce.ts:17-20` applies no coercion to them (`manual-migrations/2026-11-27-fin-ar-ap-invoices.sql`, `2026-11-27-fin-registers.sql`). There is no applied-version table. Some scripts use MariaDB-only `IF NOT EXISTS` syntax, and others are not re-runnable. Uniqueness rules `uq_units_property_unit`, `uq_customers_qatar_id` and `uq_fin_pdc_lease_cheque` live only in SQL (`manual-migrations/2026-11-24-unique-constraints.sql:5-8`) and would be lost by a `db push`. Seventeen `mst_*` tables have `Int @id` with no default (`schema.prisma:1798-1949`), the same defect that broke `fin_banks`. The recurring "insert failed, argument id is missing" patches (`2026-11-27-fin-id-autoincrement.sql`, 10 tables) show the pattern.

Secondary schema problems affect correctness more than writes. Statuses are free text in mixed case (`leases.lease_status` "DRAFT", `ar_ledgers.status` "open", `fin_pdc_register.status` "In Hand"), and only 22 enums exist, all for accounting events and procurement (`schema.prisma:3092-3290`). Money columns are nullable `Decimal(18,4)` (for example `fin_deposits.amount` at `schema.prisma:777`) while `money()` rounds to 2 decimals (`finance-rpc.ts:10`). Duplicate uniques and nullable-column uniques (`schema.prisma:626-627, 895-896, 598-600`) do not enforce what they appear to. Ledger-adjacent tables lack foreign keys (`leases.unit_id` at `schema.prisma:1726`, `fin_voucher_lines.*` at 960-965) and indexes. Parallel table families (`customers`/`fin_customers`, `pdcs`/`fin_pdc_register`, `coa_*`/`fin_coa_accounts`) let reads miss data written to the twin. One caveat: the live column state was not checked, so manual SQL may or may not match what `schema.prisma` claims. The notes also record that the provider is MySQL (`schema.prisma:5-7`), which should be reconciled with the project's memory note about `pms_db`.

## Architecture multiplies the paths and leaves ledger integrity to the client

Six layers can reach the same table: the generic proxy, dedicated REST routers, typed helpers (`db-finance.ts`, `db-masters.ts`), React Query hooks, server services, and the raw-SQL engine (`finance-rpc.ts`, `accounting.ts`, about 1340 lines). The dedicated routers appear to have almost no callers, return different response shapes, and carry their own bugs: `properties.ts:195, 206-209` mass-assigns `req.body` into Prisma, and `leases.ts:140-145` deletes a lease with no status check. The posting core (`postAccountingEvent`, sequences) is transactional and row-locked in `finance-rpc.ts`, which is sound. The orchestration around it is not atomic. `postManualVoucher` runs create and post in separate transactions, `manualPdcStatusUpdate` posts after the status update, and AR create and collect run check-then-write without locks (`accounting.ts:~1030-1090`). The manual-voucher idempotency key includes the date, so a repeat on another day posts again. `accounting.ts` has no `txn(` usages. Posted ledger lines can be changed through generic update because only delete is guarded (`db.ts:443-479` against `500-508`; inferred).

Tenant scoping is the largest latent architecture risk. Only 13 models have `tenant_id`, and the proxy applies no tenant filter, so isolation works only because a single organisation exists. `tenant_id` also means two things, organisation and renter. `tenantMiddleware` and `kv.ts:6-8` trust a spoofable `x-tenant-id` and default to a hard-coded UUID. `db-policy.ts` is deny-by-default by role, but unprefixed financial tables (`ar_ledgers`, `journal_entries`, `payments`, `receipts`, `pdcs`) fall under the staff-wide `OPERATIONS_RULE` (`db-policy.ts:30`), so any staff role can write them through `/api/db`. These are security and multi-tenancy issues rather than the cause of today's failed updates.

## Browser-held and browser-computed data remains the second major problem

Real browser storage is gone: `__root.tsx:122-129` wipes `localStorage` and `sessionStorage`, and `src/lib/kv-store.ts` is a server-backed key-value table with an in-memory map. But the migration moved the problem rather than fixing it. About 70 distinct keys hold business records as JSON blobs. `setItem` writes the cache first and fires an unawaited PUT, with failures only logged (`kv-store.ts:10-13, 38-42`). Whole arrays are read-modified-written, so concurrent users overwrite each other (`leasing-module.tsx:2170-2171, 4805-4806`; `leases-module.tsx:211-238`). The hydrated cache means other users' changes do not appear until reload.

The critical blobs are listed here. Leases: `pms_custom_lease_overrides`, `pms_renewed_leases_v1`, `pms_leasing_v2_leases`, and `pms_deleted_leases_v1`, whose default hard-codes deleted lease ids (`leases-module.tsx:595-720`; `leasing-module.tsx:4160-4175`). Cheques: `pms_renewal_pdcs`, merged into the register (`app-data-context.tsx:731`; `finance-module.tsx:7840`). Ledger: `finance_master_v1-vouchers` (`finance-store.tsx:1109, 2092`), payroll voucher copies (`payrollIntegrationService.ts:167-197`), custom chart-of-accounts accounts (`finance-module.tsx:1995-2155`) and the period lock cache `pms_posting_periods_cache` (`posting-engine.ts:655-670`). AP and procurement: `proc_ap_invoices_cache_v2`, `pms_vendor_invoices`, work orders and tickets (`proc-invoices-api.ts:72-101`; `maintenance-module.tsx:433-775`). `purge-legacy-test-data.ts:2-10` states that work orders and AP invoice tables "only ever existed in this browser's saved data", which is direct evidence these have no relational tables. Payroll "works even if DB insert fails" through a kv overlay (`hrmsService.ts:1269`). The server side of kv has no key authorisation (`kv.ts:11-35`). The audit log itself is stored in kv and can be deleted from the client (`security.ts:45-123`). Lease effective rent and dates are merged from DB plus overlays at render time (`leases-module.tsx:595-716`), so the database row is not authoritative, and a contract printout reads the override (`qatar-lease-contract.ts:459-463`).

Mock and demo data is still wired into live screens. The tenant portal routes, owner statements, the sitemap, maintenance unit lookup and `prop-mgr.manage.$id.tsx` import `mock-data.ts` (for example `portal.payments.tsx:8`, `owner.statements.tsx:5`, `sitemap[.]xml.ts:3`). The main loader falls back to an empty array, not mock data (`app-data-context.tsx:878-884`). A demo-session path remains: `auth-guards.ts:75-81` accepts a kv key `zyno-demo-session`, which any authenticated user can write, so client guards can be spoofed (client-side only, since the server still requires a session). It was not checked whether portal routes are reachable in production.

On calculation, the trial balance (`finance-store.tsx:2686-2740`; `finance-module.tsx:7401-7428`), settlement summary and final settlement (`settlement-engine.ts:82, 153, 611, 687`), reconciliations (`financial-reconciliation.ts:67-342`), invoice, late-fee and credit-note math (`revenue-billing-engine.ts:48-246`), gratuity (`hrmsService.ts:823-866`, 21/30 of basic salary per year), WPS SIF and ID normalisation (`qatar-wps-sif.ts:84-313`, where `normalizeQatarId` can fabricate an ID from a fallback seed at line 105) and statement and contract PDF totals all run in the browser from client-held data. The server also has a sub-ledger rollup (`server/services/finance.ts:11-34`), so trial balance logic is duplicated. Closed-period enforcement reads a client cache and a missing cache returns `{closed:false}`, which allows posting. Server-side period enforcement was not verified. Presentation work (PDF and HTML rendering, amount in words, date formatting, Excel export) is benign.

## Prioritised remediation

The order below puts changes that remove current failures first, then integrity, then structure.

1. Make the proxy fail loudly (days). Reject `update`/`delete` with an empty or non-primary-key `where`; return the updated row; treat zero matched rows as an error; make the shim throw or return an error that the call sites must handle; return an error for an unknown table; log the underlying Prisma error server-side with column names. Fix `fetchAllRows` to surface errors and add `.order('id')` to every paged load. Evidence: `server/routes/db.ts:456-511, 232-239`; `src/lib/db.ts:230-249`; `app-data-context.tsx:302-321`.
2. Make the filter builder faithful (days). Store filters as an array of conditions combined with AND, honour `not`, `in`, `is`, `contains` and `overlaps`, and parse alias selects like `alias:fk(...)` into Prisma includes (`src/lib/db.ts:35-163`; `coerce.ts` `buildIncludeFromSelect`). Honour the select column list or stop sending one.
3. Fix ID types on `fin_pdc_register` and `fin_legal_receivables` (1-2 weeks). Convert the tenant, property, unit and bank columns to `VarChar(36)` as done for `fin_deposits`, give `fin_pdc_register.id` an autoincrement, delete the `numericOrNull` drop path, and backfill rows that were stored with NULLs (`schema.prisma:796-809, 847-864`; `leases.ts:47, 70-76`). Add autoincrement or text ids to the 17 `mst_*` tables (`schema.prisma:1798-1949`).
4. Adopt tracked migrations (1-2 weeks). Introspect the live database into `schema.prisma`, add the SQL-only tables and columns, bring `uq_*` constraints into the schema, and use Prisma Migrate or an applied-version table. Add Int/BigInt/Decimal coercion to write paths and empty-string handling for non-string columns (`coerce.ts:23-40`).
5. Move kv business data into tables (weeks, staged). Start with the critical keys in this order: lease overrides and renewals, cheques, vouchers and payroll vouchers, custom chart-of-accounts accounts, period locks, AP and vendor invoices, work orders and tickets, settlement cases. Give each real columns, keys and optimistic-lock versions. Until then, await the PUT and surface failure, add key allow-listing and role checks to `kv.ts`, and stop hosting the audit log in kv (`kv-store.ts:10-13, 38-42`; `kv.ts:11-35`; `security.ts:45-123`).
6. Make the server authoritative for money (weeks). Enforce period closure and idempotency in the server, wrap voucher-plus-record flows (AR create/collect, manual vouchers, PDC status) in one transaction with locks, remove the date from idempotency keys, and block updates to lines of posted events (`finance-rpc.ts`; `accounting.ts:~1030-1090`; `db.ts:443-508`). Serve the trial balance and ageing from SQL so they match the ledger and survive partial loads.
7. Remove mock and demo paths (days to weeks). Replace `mock-data` in the portal and owner statements with real queries, delete the `zyno-demo-session` trust in `auth-guards.ts:75-81`, and stop the payroll kv overlay from standing in for a failed insert (`hrmsService.ts:1269`).
8. Harden tenancy and policy (as needed before a second organisation). Derive `tenant_id` only from the session, add a tenant filter in the proxy, rename the renter/organisation overload, extend `db-policy` prefixes to unprefixed financial tables, and move the `express.json` 25 MB limit after `requireSession` (`middleware.ts`; `db-policy.ts:20-30`; `server/index.ts:46, 66`).
9. Consolidate paths and clean up (ongoing). Choose the proxy or REST routers as the single write path, retire the unused one, add enums for statuses, make money columns NOT NULL where required, add missing foreign keys and indexes, and remove duplicate table families.

## Conclusion

The question "schema, architecture or data handling" resolves into one chain. Loud failures that repeat, such as BigInt against UUID or a missing column, are schema and migration problems and are cheap to fix. The intermittent "saved but not saved" and "loaded but incomplete" reports, which are harder to reproduce, come from the proxy and shim contract, where errors, zero matches and truncation look like success. This distinction matters for triage. Fixing the schema first would remove the visible errors, but it would leave the proxy returning false successes on the rest.

The storage story also changed. The move off `localStorage` did not remove local-first behaviour. It relocated it to a shared untyped table that the UI treats as the source of truth for leases, cheques and ledger entries. The database rows for those records are not authoritative, so the work is as much a data-model migration as a bug fix. All of this rests on static reading with no runtime queries, so the first action in each step should be a read-only check against `pms_db`. Examples are the real column types of `fin_pdc_register`, which migrations were applied, how many rows `app_kv_store` holds per key, and whether the alias-select and TENANT-403 findings reproduce.
